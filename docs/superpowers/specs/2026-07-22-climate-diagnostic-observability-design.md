# Climate Diagnostic Recovery Observability Design

**Date:** 22 July 2026
**Branch:** `codex/climate-fcv-output-redesign`
**Status:** Approved for implementation

## Problem

The production Climate-FCV run for assessment
`8a5d31ad-0950-4af3-9d9d-f64181bc3020` established two facts:

1. Stage 2 omitted the `%%%LENS_DIAGNOSTIC_START/END%%%` block.
2. The recovery request returned normally in about 36 seconds but the recovered
   result failed validation.

The current logs do not identify which structural requirement failed. They log
only the initial omission and the final unsuccessful recovery. A functional fix
would therefore still be speculative.

## Decision

Add bounded, structural telemetry for unsuccessful diagnostic recovery. The
telemetry will be generated by a pure helper and logged at warning level so it
is visible in the production Render logs. Successful recovery will retain the
existing info-level completion log.

## Telemetry Contract

The helper will report only low-cardinality structural facts:

- response character count;
- start- and end-delimiter presence;
- JSON parse status;
- whether the top-level value is an object;
- whether `lenses` and `findings` are lists and their bounded counts;
- whether an active Climate entry is present;
- whether Climate materiality is present and valid;
- recognized interaction direction IDs and missing required directions;
- the normalized validation failure reason.

Only fixed, allowlisted lens IDs, materiality enums, and interaction direction
IDs may appear in the summary. Arbitrary model-generated keys, identifiers, and
values will not be logged.

## Privacy and Safety

The telemetry must never contain:

- Stage 2 prose or recovery response text;
- uploaded project or contextual document content;
- prompts, evidence strings, recommendations, or geographic details;
- credentials, headers, request payloads, or provider metadata;
- arbitrary model-generated keys or values.

Tests will use sentinel sensitive text and assert that it is absent from both
the helper output and captured logs.

## Integration

`repair_lens_diagnostic()` will compute the structural summary after receiving
the provider response and validating it. When `recovered` is false, it will log
one assessment-correlated warning containing the safe summary. Exception paths
will continue to use the existing exception-class warning.

No changes will be made in this step to:

- recovery prompts, model, token limits, timeouts, or retry settings;
- diagnostic normalization or validation rules;
- SSE fields, frontend state, Stage 3 context, or report rendering;
- the Render/Azure shared lens contract.

## Testing

Test-driven implementation will cover:

1. a missing delimiter response;
2. invalid JSON between valid delimiters;
3. a Climate entry missing materiality;
4. a medium/high Climate entry missing one interaction direction;
5. an unsuccessful recovery warning containing the structural summary and
   assessment ID;
6. absence of sentinel sensitive text from summaries and logs;
7. unchanged successful-recovery and exception behavior.

Focused contract tests and the complete test suite must pass before any live
deployment or rerun is considered.

## Next Diagnostic Step

After deployment, rerun the same South Sudan assessment once. Use the new
assessment ID to identify the exact recovered structural failure. Only then
form a single root-cause hypothesis and design a functional change.
